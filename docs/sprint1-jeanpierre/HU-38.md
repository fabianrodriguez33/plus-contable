## Matriz de permisos

`ESTUDIO` = `CONTADOR` y `ADMIN` (administrador del estudio, mismos permisos).

| Opción (API `ms-tributario`) | ESTUDIO | CLIENTE_MYPE |
|---|---|---|
| Ver trabajadores · `GET /clientes/{id}/trabajadores` | ✅ | ✅ solo su cliente* |
| Registrar trabajador · `POST /clientes/{id}/trabajadores` | ✅ | ❌ 403 |
| Ver documentos · `GET /clientes/{id}/documentos` | ✅ | ✅ solo su cliente* |
| Descargar documento · `GET /clientes/{id}/documentos/{doc}/archivo` | ✅ | ✅ solo su cliente* |
| Archivar documento · `POST /clientes/{id}/documentos` | ✅ | ❌ 403 |
| Ver acuerdo · `GET /clientes/{id}/acuerdo` | ✅ | ✅ solo su cliente* |
| Guardar acuerdo · `PUT /clientes/{id}/acuerdo` | ✅ | ❌ 403 |
| Ver obligaciones · `GET /obligaciones?clienteId=`, `GET /obligaciones/{id}` | ✅ | ✅ solo su cliente* |
| Declarar · `PATCH /obligaciones/{id}/declaracion` | ✅ | ❌ 403 |
| Variar vencimiento · `PATCH /obligaciones/vencimiento` | ✅ | ❌ 403 |
| Cualquier otra ruta de `ms-tributario` | ✅ | ❌ 403 |

Sin token o con token vencido/falsificado: 401. Token sin rol: 403. Las respuestas 401/403 van sin cuerpo (Ley 29733).

\* "Solo su cliente" es la tarea 85 y **aún no está aplicado**: hoy un `CLIENTE_MYPE` puede leer las rutas de lectura
de cualquier cliente. Antes de este cambio cualquier usuario autenticado podía hacer todo, así que es una mejora, pero
no debe salir a producción sin la 85.

Implementación: [`SecurityConfig`](../../backend/ms-tributario/src/main/java/com/pluscontable/tributario/config/SecurityConfig.java)
(reglas por método y ruta, en un solo lugar). Pruebas: `PermisosPorRolTest` recorre la matriz con JWT reales.

## Propuesta para el aislamiento entre clientes (tarea 85)

**Problema:** el JWT solo trae `sub` (username) y `roles`. `ms-tributario` no sabe a qué cliente pertenece un
usuario `CLIENTE_MYPE`, y cada servicio solo accede a su propio esquema (no hay FK entre `auth_schema` y
`tributario_schema`).

**Propuesta (recomendada): claim `clienteId` en el token.**

1. **ms-auth (HU-37 / Ricardo):** agregar `auth_schema.usuarios.cliente_id BIGINT NULL` (sin FK, es de otro
   esquema). Se llena al crear la cuenta del cliente MYPE con el id del cliente de `ms-tributario`; es obligatorio
   si el usuario tiene rol `CLIENTE_MYPE` y nulo para el estudio.
2. **ms-auth (HU-36):** `JwtProvider.generate` añade `.claim("clienteId", usuario.getClienteId())` cuando no es nulo.
3. **ms-tributario (HU-38):**
   - `JwtFilter` guarda el `clienteId` del token en la autenticación (por ejemplo como `details`).
   - Un componente `AccesoCliente.exigir(Long clienteId)` que, si el usuario es `CLIENTE_MYPE`, compara con el claim.
   - Se llama en las lecturas: con `{clienteId}` de la ruta (trabajadores, documentos, acuerdo, `?clienteId=`) y,
     para `GET /obligaciones/{id}`, con el `clienteId` de la obligación ya cargada.
   - Si no coincide se responde **404**, igual que si no existiera, para no revelar qué clientes hay.
   - Las listas sin filtro de cliente (si aparecen) deben forzar el `clienteId` del token para el `CLIENTE_MYPE`.

**Por qué así:** la comprobación es una comparación en memoria, sin llamadas entre servicios ni consultas extra, y
no rompe la regla de un esquema por servicio.

**Alternativa:** guardar el RUC en lugar del id (`usuarios.cliente_ruc`) y resolver RUC → id en `ms-tributario` con
`ClienteRepository.findByRuc`. Desacopla los ids entre servicios, pero suma una consulta por petición.

**Pendiente de acordar con Ricardo:** nombre del claim, quién llena `cliente_id` al crear la cuenta (HU-37) y que
ms-auth siembre el rol `CLIENTE_MYPE`.
